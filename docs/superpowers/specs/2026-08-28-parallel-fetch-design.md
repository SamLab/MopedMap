# Дизайн: параллельная загрузка каналов в `fetch_all`

**Дата:** 28.08.2026
**Статус:** одобрено пользователем (рекомендуемый вариант; ограничение числа воркеров — при необходимости позже)

> Примечание: кэш GeoJSON (24ч) в этот дизайн НЕ входит — отложен отдельной задачей. Здесь только параллельная загрузка каналов.

## Цель

Ускорить сбор данных. Текущий узкий край — последовательная сетевая загрузка ~10 Telegram-каналов в `fetch_all` (mopedmap.py:4331): каждый канал тянется по очереди, до 20 страниц HTTP. Время сбора ≈ суммарная длительность запросов всех каналов. CPU-обработка уже оптимизирована ранее (n-граммный предфильтр, коммит `9eddeed`), поэтому оптимизируем именно сетевой этап.

## Подход

Распараллелить загрузку каналов через `ThreadPoolExecutor`. Для HTTP-bound I/O потоки оптимальны: GIL не препятствует ожиданию сети, а запуск потоков дешёвый.

## Архитектура

### 1. Рефакторинг `fetch_all`

Вынести «список задач-замыканий» в отдельную внутреннюю возможность, чтобы пул можно было тестировать без реальной сети:

- Новая вспомогательная функция `_fetch_posts_parallel(jobs, max_workers)`:
  - `jobs` — итерируемый `(index, callable)`; `callable()` возвращает `list[post]`.
  - Собирает результаты в `{index: posts}` (вставляя `[]` при исключении в воркере).
  - Возвращает список постов, конкатенированный в порядке `index` (восстанавливает исходный порядок каналов).
  - Каждая задача оборачивается в try/except: исключение в одном воркере НЕ роняет остальные (возвращает `[]` для этого индекса).

- `fetch_all(hours_filter=None)` переписывается на:
  ```python
  jobs = []
  for i, ch in enumerate(CHANNELS):
      jobs.append((i, lambda h=hours_filter, u=ch["url"], n=ch["name"]: fetch_channel(u, n, h)))
  jobs.append((len(CHANNELS), lambda h=hours_filter: fetch_radarmap_api(h)))
  workers = min(os.cpu_count() or 1, len(jobs))
  posts = _fetch_posts_parallel(jobs, max_workers=workers)
  print(f"Всего загружено: {len(posts)} постов")
  return posts
  ```
  - `fetch_radarmap_api` включается в тот же пул (независимый единственный HTTP-вызов).
  - Печать «name: N постов» остаётся внутри `fetch_channel`/`fetch_radarmap_api` → её порядок в логе становится недетерминированным. Это косметика, допустимо.

### 2. Порядок

Порядок результирующего списка постов = порядок CHANNELS (+ API в конце), как и сейчас. Порядок НЕ влияет на итоговые маркеры (они сортируются/дедупятся в `process_posts`/`generate_html`), но сохранение прежней конкатенации исключает любую регрессию.

### 3. Обработка ошибок

- `fetch_channel` и `fetch_radarmap_api` уже ловят исключения и возвращают `[]` — собственно сетевые сбои уже безопасны.
- `_fetch_posts_parallel` дополнительно гарантирует: если воркер упадёт с непойманным исключением, для его индекса возвращается `[]`, а общий прогон продолжается.

### 4. Число воркеров

`min(os.cpu_count() or 1, len(jobs))` — не больше числа задач. При ~10 каналах это ~10 потоков. Ограничение сверху (например, 3-4) — отложенное решение, применим только если Telegram начнёт ограничивать параллельные web-превью.

## Тестирование (TDD)

Отдельная единица, тестируемая без сети — `_fetch_posts_parallel(jobs, max_workers)`:
- **RED-тесты** (новый `test_fetch_parallel.py`, временный):
  1. Несколько джобов возвращают результаты, порядок сохранён по `index`.
  2. Джоб, бросающий исключение → `[]` для его индекса, остальные результаты сохранены (прогон не роняет).
  3. Пустой список джобов → пустой результат.
- После реализации — GREEN.
- Регрессия: быстрый прогон `fetch_all` не обязателен (сеть медленная/вариабельная); достаточно, что `mopedmap.py` синтаксически корректен и существующие маркер-кейсы не меняются. Полный live-прогон — по желанию.

## Риски

- **Rate-limit Telegram** при одновременных запросах — маловероятен при ~10 параллельных, влияет только на полноту (ошибка → канал пропущен), не на корректность. При проявлении — уменьшить `max_workers`.
- **Порядок печати лога** недетерминирован (косметика).
- **`os.cpu_count()`** может вернуть `None` в редких средах — фолбэк `or 1`.
